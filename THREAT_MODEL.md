# Sycophant Threat Model

**The pods that execute LLM-driven code (harness, capability-job) are adversarial, and the rest of the cluster stays safe regardless of what they do.**

The harness pod hosts an autonomous LLM agent that processes untrusted inputs: user prompts, tool results, model outputs, retrieved documents. Any of those inputs can subvert the agent's behavior (prompt injection, poisoned tool output, model compromise). Once subverted, the agent acts with the full authority of the harness pod. **Therefore every privilege the harness pod carries is exploit surface for the agent itself.** The mitigation is structural: refuse to grant the harness anything that could be misused if the agent is subverted. This is the principle behind narrow single-audience tokens, `automountServiceAccountToken: false`, zero-RBAC agent SA, and credentials the proxy names but never holds. Granting plural-audience tokens or broad RBAC anywhere on the harness surface defeats this mitigation.

A fully compromised agent must not be able to:

0. **See secrets**: LLM API keys and tool credentials are Kubernetes Secrets. An LLM API key is the inference command's `secret`. A tool credential is a `secret.<toolset>.<name>: <path>` key on the agent command. The agent requests actions by name. The harness has zero Secret RBAC: it names the Secret in the Job spec and never reads its value. The kubelet mounts that value read-only (mode 0o440) only into the short-lived model-call or tool-job pod, and only while that call runs. A keepalive toolset's pod is the exception: it keeps the value between calls until it has been idle for 10 minutes. The runtime in that pod copies it to its path with mode 0o600. The plaintext never appears in a Job spec, a gRPC message, or the harness pod's memory, env, or filesystem. **This is the load-bearing clause.**

1. **Exfiltrate**: reach network destinations its toolset didn't declare. This is enforced by a Cilium L7 DNS FQDN allowlist, egress default-deny on the harness, and per-profile CiliumNetworkPolicies on capability-job pods, composed additively on the fail-closed namespace `default-deny-egress` floor. Secrets and egress are scoped per toolset, not per call: every call of a toolset gets all of that toolset's Secrets and egress domains, so any of a toolset's Secrets can reach any of its domains. An agent that needs a different set is a different agent.

2. **Forge history**: write, hide, or rewrite conversation log entries. The harness is the sole author of conversation log entries. Its history PVC is separate from the toolset-mounted workspace PVC, so the agent's runtime cannot write them directly.

3. **Impersonate**: present as a different agent, tenant, or trusted in-cluster service. The mechanisms are audience-bound SA tokens (KEP-1205) with one audience per pair (harness→toolset, harness→relay, channel→relay), the CiliumNetworkPolicies that admit only relay-controller to the harness's HarnessControl port and only the harness to each capability-job pod, server-minted `channel_stream_id`, and per-request Kubernetes access reviews on the external surface — the subject is resolved by a TokenReview of the person's OIDC token on the person path, or by the operator's handle binding for the TokenReview-authenticated channel on the channel port, and a SubjectAccessReview for that subject, under the relay's own credential, on every path, answers whether it reaches the named agent.

4. **Escape**: break out of its sandbox to host kernel, other tenants' pods, or the cluster-control plane. gVisor (or operator-opted Kata) `runtimeClassName` is mandatory on the `capability-job` toolsets (and channels) that run agent-executed tool code, enforced by the `cluster-gvisor-pod-policy` ValidatingAdmissionPolicy. The harness runs on the kubelet-default runtime with seccomp `RuntimeDefault` as the compensating control. All agent pods share the same baseline: PSA restricted, perimeter CiliumNetworkPolicies, drop-`ALL` capabilities, `readOnlyRootFilesystem`, `runAsNonRoot`.

5. **Disarm**: tamper with the policy machinery (Kyverno, VAP, CiliumNetworkPolicies, RBAC) that enforces 0–4. The `cluster-protect-security` Kyverno ValidatingPolicy denies same-namespace edits to CiliumNetworkPolicies, NetworkPolicies, RBAC, ServiceAccounts, and ConfigMaps. The Kyverno policies themselves, and the cluster VAPs and their bindings in `admissionregistration.k8s.io`, are not guarded at admission; they are protected by RBAC absence instead: the agent runtime SA is bound to no Role or ClusterRole at all, so it holds no verbs on any resource, the policy machinery included. Cluster-wide, write on the Kyverno policy CRDs and on the cluster VAPs and their bindings is held only by `cluster-admin` and the break-glass `cluster-chart-admin`, which is bound to nobody by default. Write on `ciliumnetworkpolicies` and `clusterrolebindings` is additionally held by Kyverno's own background-controller, and write on `ciliumnetworkpolicies` by `provision-write` (bound per-namespace to the per-install installer SAs `provision-<kind>-<handle>`, one per tenant, agent, user, toolset, inference, and channel provision command); an agent can reach neither.

## Beyond the core model: controller blast radius

The clauses above assume the controllers are trusted. Defense in depth bounds them anyway. The chief concern is the relay-controller, the one controller that terminates the external client surface and so is the most exposed:

- The relay-controller holds no Secrets RBAC at all: a compromised relay has nowhere to plant or read a Secret in its namespace. The `cluster-channel-secret-name-allowlist` ValidatingAdmissionPolicy additionally bounds the tailnet channel's ServiceAccount to the fixed `tailnet-identity` Secret (one tailnet channel per tenant) even though the channel's Role grants unconstrained `secrets: create` (Kubernetes ignores `resourceNames` on the `create` verb). A compromised relay also cannot rewrite the identity data it answers from: the `cluster-protect-security` Kyverno ValidatingPolicy denies same-namespace writes to the `relay-identity` ConfigMaps, and the relay's own Role is read-only on ConfigMaps.
- Only the per-tenant `ag-<agent>` SA may create `capability-job`-labeled Jobs (`cluster-protect-security`), so no other in-namespace identity can spawn adversarial workloads under that label.

## Why

Without clause 0, sycophant is "a sandboxed prompt-injection target that leaks the API key on first exploit." That the harness creates both the model-call and tool-call Jobs through one mechanism — naming credentials it never reads — is the entire reason the architecture exists. The harness reads its own instructions in-process from a read-only volume, and reaches every credential only by name — no network hop and no Secret access. Clauses 1–5 protect clause 0 from being bypassed by any other route.

## How to apply

Any security or test-coverage discussion starts here. Lead with the thesis sentence, then the clauses, with 0 marked as load-bearing. Mechanisms (gVisor, VAP, CNP, audience binding, etc.) are never the headline. They are how a specific clause is enforced. Never present these as a flat list. The structure (one thesis → six clauses → mechanisms) is the point.
