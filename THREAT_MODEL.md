# Sycophant Threat Model

**The pods that execute LLM-driven code (harness, capability-job) are adversarial, and the rest of the cluster stays safe regardless of what they do.**

The harness pod hosts an LLM agent that reads untrusted input: user prompts, tool results, model output and retrieved documents. Any of it can subvert the agent through prompt injection, poisoned tool output or a compromised model. A subverted agent holds whatever the harness holds, so the harness holds nothing worth taking. A plural-audience token or broad RBAC anywhere on the harness breaks this.

A fully compromised agent must not be able to:

0. **See secrets**. This is the load-bearing clause. Clauses 1 to 5 exist so no other route gets around it. The harness names Secrets and never reads them. LLM API keys and tool credentials are Kubernetes Secrets, and the agent asks for actions by name. The harness has no Secret RBAC. It creates model-call and tool-call Jobs the same way: it names the Secret in the Job spec. The kubelet mounts the value read-only into that short-lived pod, only for that call. A keepalive toolset's pod is the exception. It keeps the value between calls until it has been idle for 10 minutes. The plaintext never appears in a Job spec, a gRPC message, or the harness pod's memory, env or filesystem. The harness reads its own instructions in-process from a read-only volume. In config, an LLM API key is the inference command's `secret`, and a tool credential is a `secret.<toolset>.<name>: <path>` key on the agent command. The kubelet mounts it with mode 0o440. In a keepalive pod, the runtime copies it to its path with mode 0o600.

1. **Exfiltrate**: reach a network destination its toolset didn't declare. A Cilium L7 DNS FQDN allowlist, default-deny egress on the harness, and per-profile CiliumNetworkPolicies on capability-job pods enforce this. They add up on top of the fail-closed namespace `default-deny-egress` floor. Secrets and egress are scoped per toolset, not per call. Every call of a toolset gets all of its Secrets and egress domains, so any of its Secrets can reach any of its domains. An agent that needs a different set is a different agent.

2. **Forge history**: write, hide or rewrite conversation log entries. The harness is the sole author of those entries. Its conversation volume is separate from the workspace volume that toolsets mount, so the agent's runtime cannot write them directly.

3. **Impersonate**: pose as a different agent, tenant or trusted in-cluster service. Each ServiceAccount token is bound to one audience per pair: harness to toolset, harness to relay, and channel to relay. CiliumNetworkPolicies let only relay-controller reach the harness's HarnessControl port, and only the harness reach each capability-job pod. The server mints `channel_stream_id`. The relay checks every request on the external surface with Kubernetes access reviews, under its own credential. On the person path, a token review of the person's OIDC token names the subject. On the channel port, the channel authenticates by token review, and the operator's handle binding names the subject. On every path, a subject access review then asks whether that subject may reach the named agent.

4. **Escape**: break out of its sandbox to the host kernel, other tenants' pods or the cluster control plane. A gVisor `runtimeClassName` is mandatory on the `capability-job` toolsets and channels that execute agent tool code. The `cluster-gvisor-pod-policy` ValidatingAdmissionPolicy enforces it. The harness uses the kubelet's default runtime, with seccomp `RuntimeDefault` as the compensating control. All agent pods share one baseline: Pod Security Admission restricted, perimeter CiliumNetworkPolicies, drop-`ALL` capabilities, `readOnlyRootFilesystem`, `runAsNonRoot`.

5. **Disarm**: tamper with the policy machinery (Kyverno, ValidatingAdmissionPolicies, CiliumNetworkPolicies, RBAC) that enforces 0 to 4. An agent holds no permissions, and the few roles that can change policy belong to nobody it can reach. The agent runtime ServiceAccount is bound to no Role or ClusterRole, so it holds no verbs on any resource. The harness pod also sets `automountServiceAccountToken: false`. The `cluster-protect-security` Kyverno ValidatingPolicy denies same-namespace edits to CiliumNetworkPolicies, NetworkPolicies, RBAC, ServiceAccounts and ConfigMaps. Admission does not guard the Kyverno policies, or the cluster ValidatingAdmissionPolicies and their bindings in `admissionregistration.k8s.io`. Missing RBAC guards them instead. Cluster-wide, only `cluster-admin` and the break-glass `cluster-chart-admin` can write them. `cluster-chart-admin` is bound to nobody by default. Kyverno's own background-controller can also write `ciliumnetworkpolicies` and `clusterrolebindings`. `provision-write` can also write `ciliumnetworkpolicies`. It is bound per namespace to the per-install installer ServiceAccounts `provision-<kind>-<handle>`, one per tenant, agent, user, toolset, inference and channel provision command. An agent can reach neither.

## Beyond the core model: controller blast radius

The clauses above assume the controllers are trusted. Defense in depth bounds them anyway. The chief concern is the relay-controller. It terminates the external client surface, so it is the most exposed:

- The relay-controller holds no Secrets RBAC. A compromised relay can't plant or read a Secret in its namespace. The `cluster-channel-secret-name-allowlist` ValidatingAdmissionPolicy also bounds the tailnet channel's ServiceAccount to the fixed `tailnet-identity` Secret (one tailnet channel per tenant). This holds even though the channel's Role grants unconstrained `secrets: create`, since Kubernetes ignores `resourceNames` on the `create` verb. A compromised relay also cannot rewrite the identity data it answers from. `cluster-protect-security` denies same-namespace writes to the `relay-identity` ConfigMaps, and the relay's own Role is read-only on ConfigMaps.
- Only the per-tenant `ag-<agent>` ServiceAccount may create `capability-job`-labeled Jobs (`cluster-protect-security`). No other identity in the namespace can spawn adversarial workloads under that label.

## How to apply

Start any security or test-coverage discussion here. Lead with the thesis, then the clauses, then the mechanisms that enforce each one. Mechanisms are never the headline and never a flat list.
